# Micronaut AOT Agent Guidance

This repository contains Micronaut AOT, a build-time optimizer framework used by
Micronaut build tooling. Keep changes narrow and verify them against the module
that owns the behavior.

## Repository Map

- `aot-core` contains the optimizer SPI, source-generation context, metadata
  loading, and application-context analysis.
- `aot-api` exposes the public entry point used by build and CLI integrations,
  mainly `MicronautAotOptimizer`.
- `aot-std-optimizers` contains the built-in optimizers registered through
  `META-INF/services/io.micronaut.aot.core.AOTCodeGenerator`.
- `aot-cli` contains the `micronaut-aot` command and classloader isolation used
  by build plugins.
- `aot-bom` publishes dependency alignment.
- `src/main/docs/guide` contains the user guide. `toc.yml` is the navigation
  source of truth.

## Coding Notes

- `.sdkmanrc` and CI use Java 25. Keep contributor guidance, CI expectations,
  and source/tooling changes aligned with that baseline.
- AOT analysis runs against user application classpaths. Avoid dependency or
  classloader changes that cause the optimizer to see Micronaut customizations
  from the wrong classloader.
- Most Micronaut runtime dependencies in optimizer modules should stay
  `compileOnlyApi`; the analyzed application supplies its own Micronaut runtime.
- New standard optimizers usually need all of these in sync:
  implementation class, `@AOTModule` metadata, service-loader entry, tests, and
  generated configuration documentation.
- Treat generated source and resource output as runtime-sensitive. Check both
  JIT and native runtime paths when changing `Runtime`, GraalVM configuration,
  service loading, environment deduction, or application-context configuration.

## Contributing Guidelines

- Before opening or updating a pull request, read this repository's
  `CONTRIBUTING.md` and any maintainer guidance such as `MAINTAINING.md` when
  present, then follow every repo-specific PR requirement they name.
- Treat requirements in contributor docs and any PR template checklist items, if
  present, as handoff requirements. If a requirement is not applicable, state
  that explicitly in the PR description or handoff note.
- For UI-visible changes, confirm whether screenshots or other visual evidence
  are required and include them in the PR description; if screenshots cannot be
  provided, explain why and describe the verification that was performed.

## Documentation

- Guide files live under `src/main/docs/guide`.
- Update `src/main/docs/guide/toc.yml` whenever adding, removing, or moving
  guide sections.
- Build the guide with `./gradlew publishGuide` or `./gradlew pG`; `./gradlew
  docs` also builds Javadocs.
- Optimizer configuration reference content is generated by
  `:aot-std-optimizers:generateConfigProps` from the `@AOTModule` and `Option`
  metadata. Prefer fixing metadata over hand-editing generated reference text.
- This repository has no `doc-examples` directory at the time of writing. Keep
  examples in the guide or tests unless a real executable examples module is
  added.
- Release note labels are configured in `.github/release.yml`; use `type: docs`
  for documentation-only changes.

## Verification

- Root Markdown guidance changes: run `git diff --check`.
- Guide changes under `src/main/docs/guide`: run `./gradlew publishGuide`.
- Module code changes: run the affected module tests, for example
  `./gradlew :aot-core:test`, `./gradlew :aot-std-optimizers:test`, or
  `./gradlew :aot-cli:test`.
- CLI behavior changes: include `./gradlew :aot-cli:test`.
- Standard optimizer changes: include `./gradlew :aot-std-optimizers:test` and
  `./gradlew :aot-std-optimizers:generateConfigProps`.
- Broad changes or pre-PR confidence: run `./gradlew check` and `./gradlew docs`.
