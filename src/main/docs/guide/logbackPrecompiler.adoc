The `micronaut-aot-logback` module compiles an application's `logback.xml` into a Logback `Configurator` at build time.
Without a `Configurator` service, Logback parses `logback.xml` with its Joran framework on the main thread at every start.
An application that carries the generated configurator does neither.

WARNING: This module is experimental: its API, the names it generates and its rules may change.

Unlike the `logback.xml.to.java` optimizer, this module is not an AOT optimizer.
It does not start the application, uses no `AOTContext`, and needs no AOT run: a build tool calls it in-process with plain paths and gets class files back.
Its artifact, `io.micronaut.aot:micronaut-aot-logback`, has no dependencies.
It is meant for build tool plugins and packagers, not for applications.

The engine fails closed.
Whenever it cannot prove that the generated code builds exactly the `LoggerContext` Joran builds, it generates nothing and says why, and Logback reads `logback.xml` at startup as it always did.
It also stands down when a `Configurator` is already registered on the class path it is given, which is the case for an application that `logback.xml.to.java` has already optimized.
It cannot see an optimizer that runs later, on an application that already carries its output: a build that applies both has to decide which one configures Logback.

== Calling it

The inputs are:

[cols="1,3"]
|===
|Input |Meaning

|`applicationOutput`
|The application's own output in class path order: its resource roots and its class directories, or a jar. Pass the class directories as well as the resources: the engine stands down when the application carries a Logback or SLF4J class, or a `Configurator` service file, which an annotation processor writes to the class output. When two roots hold the same name, the first wins, except for `logback.xml`: when two roots have one, the engine stands down.

|`runtimeClasspath`
|The runtime class path after the application, in order: jars or directories. The engine takes logback-classic, logback-core and slf4j-api from here, never from the caller's own class path.

|`targetRelease`
|The lowest Java release the application runs on. The generated classes are class files of Java 25, so the engine stands down below 25.

|`closedClassPath`
|`true` only when the class path given here is exactly the one the application runs on. `false` by default. See <<logbackPrecompilerGuards, Guards for open class paths>>.

|`workDirectory`
|Where the engine unpacks its front end. A temporary directory, deleted afterwards, when unset.
|===

The `Result` has a `status()`, one `message()` for the caller to log, and the generated `entries()`:

* `GENERATED`: the message says what was compiled. `writeTo` writes the entries below a directory, which has to be on the application's class path next to its `logback.xml`. A packager can add `entries()` to an archive instead.
* `STOOD_DOWN`: nothing was generated, and the message names the reason. This is expected for many applications.
* `FAILED`: nothing was generated because a generated name is already taken, the output of an earlier call is still in the application output, the class path could not be read, or the engine failed. The message is worth a warning.

`precompile` never throws for anything about its inputs, so a build that calls it does not fail because of Logback.
`writeTo` only writes: removing the output of an earlier build is the caller's job.
A caller that writes into one of the application roots it passes, such as the class directory, has to remove that output before it calls `precompile` again, not after. While it is there the result is `FAILED` and the earlier output stays in use, whatever has changed in the application since.
The output is the service file and the classes of the package `io.micronaut.aot.logback.generated`.
`logback.xml` has to stay in the application, because the fallbacks below read it.

`LogbackPrecompiler.applicationInputs()` returns, as Ant-style patterns, the entries of the application output that can change the result.
A build tool may declare its inputs with them, so that the step stays up to date when ordinary classes and resources change.
Of everything else in the application output the engine reads the name and nothing more.
On the runtime class path it reads the names of every entry, the manifests of logback-classic and logback-core, and the packaged `application*` and `bootstrap*` configuration files of every entry.

The engine never loads application classes.
It reads `logback.xml` with Logback's own parser and model builder, taken from the application's Logback jars, in an isolated class loader.
It instantiates only the `ch.qos.logback` classes the file names, and never starts an appender.

== What it generates

Three classes in the package `io.micronaut.aot.logback.generated` and one service file:

* `LogbackConfigurator`, the configurator, as a class file of Java 25;
* `JoranFallback`, which every path that hands over to Joran goes through, so that the literal path never loads Joran;
* `ClassPathGuard`, unless the class path is closed;
* `META-INF/services/ch.qos.logback.classic.spi.Configurator`.

== The subset

The engine compiles a `logback.xml` made of:

* appenders of public `ch.qos.logback` classes with `String`, `boolean` or `int` properties and at most one `PatternLayoutEncoder` with a pattern;
* loggers, the root logger and appender references.

Everything else stands the engine down, and the message names the element: variables, `<property>`, `<include>`, `<if>`, `<conversionRule>`, filters, rolling policies, custom appenders and a `<configuration>` with `debug`, `scan` or `packagingData` on.
So does what Joran itself corrects: two appenders with the same `<file>`, a property element without text, a `<name>` element inside an appender.
The `logback.xml` that Micronaut Launch generates is inside the subset.

== When it stands down

Besides a file outside the subset, the engine generates nothing when:

* `targetRelease` is below 25;
* the application output carries a Logback or SLF4J class of its own;
* logback-classic, logback-core or slf4j-api is missing, a Logback jar declares no `Implementation-Version`, the two versions differ, or the version is outside the tested range, which is `[1.5.37, 1.6)`;
* there is no `logback.xml`, or more than one class path entry or more than one application root has one, which Logback reports at startup;
* any class path entry has a `logback-test.xml`, a `logback.groovy` or a versioned Logback file under `META-INF/versions/`;
* any entry of the class path it is given already registers a `Configurator`;
* a packaged `application*` or `bootstrap*` configuration file, at the root or under `config/` of an application root or of any entry of the runtime class path, may set `logger.config` or `logback.configurationFile`. Micronaut applies such a location only without a `Configurator` service, and the generated code cannot see it (see <<logbackPrecompilerLocations, Locations only Micronaut sees>>). Every such file is read, also one that an earlier entry has under the same name: Micronaut reads the file of a dependency when the application has none of that name, and it can merge the files of every entry, depending on its configuration loading strategy. The names are wider than what Micronaut reads by default, which is `application` and `bootstrap`, with an optional environment suffix, at the root of the class path: `config/` is read only when `overrideConfigLocations` adds a location such as `classpath:config/`. A false positive only costs the optimisation.

== What the configurator does at run time

On every call, in this order:

. If the `logback.configurationFile` system property is set, it runs Logback's own default lookup.
. On a second or later call, which is Micronaut's logging refresh, it configures from the first of these that is set: an environment variable named `logback.configurationFile`, the `logger.config` system property, the `LOGGER_CONFIG` environment variable, an environment variable named `logger.config`.
. If `logback.debug` or `logback.statusListenerClass` is set, or `-Dmicronaut.logback.precompiled=false`, it runs Logback's default lookup.
. On an open class path, if a guard fails, it runs Logback's default lookup.
. Otherwise it applies the content of `logback.xml` literally, in Joran's order.

`-Dmicronaut.logback.precompiled=false` is the opt-out: with it every call hands over to Joran. It does not bring back a location that only Micronaut sees, described below.

[[logbackPrecompilerLocations]]
=== Locations only Micronaut sees

Micronaut applies `logger.config`, or a `logback.configurationFile` of its own configuration, on its logging refresh. When any `logger.*` property is set, that refresh runs at startup and again on every refresh event.
Without a `Configurator` service it configures Logback from that location.
With one, it calls the service's `configure(LoggerContext)` and passes it nothing else: the location stays in Micronaut's `LogbackLoggingSystem`, and Micronaut copies it neither into a system property nor into the `LoggerContext`.

So the generated configurator applies a location only where it can read it itself, as the first two rules above list: the `logback.configurationFile` and `logger.config` system properties, and the `logback.configurationFile`, `LOGGER_CONFIG` and `logger.config` environment variables.
A location that comes from any other property source is not applied, and the compiled configuration stays in use:

* a program argument, such as `java -jar app.jar --logger.config=custom.xml`. A `-Dlogger.config=custom.xml` written after the jar or the main class is a program argument too, not a system property: Micronaut keeps it in the property source of its command line. The configurator does not read the command line of the process instead, from the `sun.java.command` property or from `ProcessHandle.current().info().arguments()`: the command line does not say which arguments the application passed to Micronaut, and it is only one of the sources listed here;
* a configuration file outside the class path, such as `config/application.yml` in the working directory or a file named by `micronaut.config.files`;
* any other property source, such as distributed configuration or properties passed to `ApplicationContext.builder()`.

Pass the location as a JVM system property, `java -Dlogger.config=custom.xml -jar app.jar`, or as the `LOGGER_CONFIG` environment variable instead.
The opt-out does not help: the configurator then runs Logback's default lookup, which reads `logback.xml`, because Micronaut still calls the configurator instead of reading the location.
https://github.com/micronaut-projects/micronaut-core/issues/13390[micronaut-core#13390] proposes that Micronaut's refresh apply such a location itself, whatever `Configurator` is registered.
A packaged configuration file is the one source the build can read, so it stands down when one might set the location.

[[logbackPrecompilerGuards]]
== Guards for open class paths

Outside a packaging that fixes the class path, the class path can change after the build: a later test run sees the same output directory, an IDE leaves stale output, a file is mounted into a container image.
So unless the caller sets `closedClassPath(true)`, the configurator hands over to Joran when:

* a `logback-test.xml` is visible, or
* the first visible `logback.xml` is missing, or differs from the compiled file in size or CRC-32.

It looks where Joran would, through the class loader that defines logback-classic, and it looks again on every call.
So a `logback.xml` that is edited while the application runs is read by Joran on the next logging refresh, as it would be without the generated configurator.
Each call costs two class loader lookups, one read of `logback.xml` and its CRC-32.
Logback calls the configurator once when it initialises, and Micronaut once per logging refresh, which it runs only when a `logger.*` property is set; a log call never runs the guards.
The first call costs a few milliseconds, most of it the class loader's first lookups, which the application makes later anyway; every later call takes well under a millisecond.

The guards have limits. After any of these changes the generated configurator is still applied, although Joran would give another result:

* A second `logback.xml` is added to the class path after the build. Logback would report it at startup.
* The class path changes in another way that the build checked. Nothing but the two guards is checked again at run time: not the Logback version, not a `Configurator` that another entry registers, not a packaged `logger.config`. With a Logback outside the tested range, the generated classes are untested and may not even link.

Build again after such a change, or start the application with `-Dmicronaut.logback.precompiled=false`.

`closedClassPath(true)` is for a packager whose archive is the whole class path. The build-time checks then guarantee what the guards check, and `ClassPathGuard` is not generated.
