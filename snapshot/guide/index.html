Micronaut AOT

Build time optimizations for Micronaut

Version: 3.2.0-SNAPSHOT

1 Introduction

Unlike other Micronaut modules, Micronaut AOT is not a dependency which needs to be added to your application: it’s a framework which requires integration with your build process: it is typically aimed at being integrated into build tool plugins. If you are looking into documentation about how to configure Micronaut AOT, you should look into the corresponding build tool documentation. Micronaut AOT support is implemented by the Micronaut Gradle plugin and Micronaut Maven plugin.

Micronaut AOT is a framework which implements ahead-of-time (AOT) optimizations for Micronaut application and libraries. Those optimizations consist of computing at build time things which would normally be done at runtime. This includes, but is not limited to:

  • pre-parsing configuration files (yaml, properties, …​)

  • pre-computing bean requirements in order to reduce startup time

  • performing substitution of classes with "optimized" versions for a particular environment

Micronaut AOT can generate specific optimizations for different environments, in particular, it can make a difference between optimizations needed in JIT mode (traditional JVM applications) and native mode (application compiled with GraalVM native-image).

3 Quick Start

Applicability

The goal of Micronaut AOT is to create an optimized "binary" for a particular deployment environment. It is not to make development experience faster: because build time optimizations require deep analysis of the application, it will actually make the local development slower if you use optimized binaries.

You should consider Micronaut AOT similarly to what GraalVM’s native-image tool is: a "compiler" which generates a different application, aimed at a particular runtime. That is, depending on the optimizations which are enabled, a binary optimized by AOT may, or may not, work in a specific deployment environment.

As a consequence, it is recommended to build your Micronaut AOT optimized application on the same environment as the deployment one. Please refer to the documentation of your build tool for configuration options.

The following documentation is for users who want to implement their own AOT optimizers.

Micronaut AOT projects

The Micronaut AOT project consists of 5 main modules:

  • micronaut-aot-core provides the APIs for implementing "AOT optimizers", or code generators.

  • micronaut-aot-api exposes the public API for interacting with the AOT compiler. It mostly consists of the MicronautAotOptimizer class which is responsible for loading the different AOT modules via service loading, then driving the AOT process.

  • micronaut-aot-std-optimizers implements a number of standard Micronaut AOT optimizers.

  • micronaut-aot-cli is the command line tool responsible for invoking the AOT compiler. It is recommended to integrate with Micronaut AOT via this CLI to ensure proper classloader isolation.

  • micronaut-aot-logback compiles an application’s logback.xml into a Logback Configurator at build time. The Micronaut build plugins call it; its API is internal to them. It is independent of the other modules and of the AOT compiler: see Precompiling logback.xml.

How it works

Optimization process

Micronaut AOT is a post-processing tool. By that, we mean that it takes the output of regular Micronaut application compilation, then performs an analysis of this and generates new classes, resources, etc. which are then used to create a new binary (jar, native binary, …​).

In a nutshell, the inputs of Micronaut AOT are:

  • the application runtime classpath

  • the Micronaut AOT runtime (including the AOT optimizers)

  • the AOT optimizer configuration (including the target runtime, e.g JIT vs native)

And its outputs are:

  • generated source files and their compiled (.class) versions

  • generated resource files

  • a list of resources which should be removed from the final binary (for example, if a YAML file is replaced with Java configuration, a class would be generated, but then we know we don’t need the YAML file anymore in the final binary)

  • log files (to diagnose what happened during the AOT process)

The MicronautAotOptimizer class is a special case of code generator which integrates the dynamically loaded AOT optimizers, and generates an ApplicationContextConfigurer which will initialize the optimizations.

It’s then the responsibility of integrators to take those outputs to generate different binaries.

User-code loading

In order to perform optimizations, so called optimizers (or AOT modules) are used. Those modules need access to the application context, so that they can, for example, determine if a bean is going to be needed in a particular deployment environment. Or, they may need access to the configuration which is dynamically loaded from an external source (think of distributed configuration) to generate static configuration instead.

Therefore, the AOT compiler needs to be executed in the same classloader as the application code itself. This is why there are 2 different classpaths for the AOT compiler:

  • the application classpath corresponds to the application runtime classpath. It is, technically speaking, the result of previous compilation plus all transitive dependencies needed by the application (or library).

  • the AOT classpath, which is the classpath of the AOT compiler and the AOT optimizers.

The role of the application context configurers

Given the application classpath, the AOT compiler will instantiate an ApplicationContext, which will have all the context configurers (classes implementing the ApplicationContextConfigurer interface and annotated with @ContextConfigurer) applied automatically. This is how the AOT compiler will "know" about particular application context customizations which can be done by a user.

Therefore, it is critical to understand that the AOT compiler cannot figure out arbitrary application context customizations. For example, in the following code:

class Application {
    public static void main(String... args) {
        Micronaut.build(args)
            .environmentPropertySource(false)
            .mainClass(Application.class)
            .start();
    }
}

there’s an environmentPropertySource() call which is opaque to the AOT compiler: it cannot know that the application is configured that way (for this it would actually have to start the application and perform runtime interception which would be too expensive or impossible).

Therefore, all customizations need to be done using a different pattern:

class Application {
    @ContextConfigurer
    public static class MyConfigurer implements ApplicationContextConfigurer {
        @Override
        public void configure(ApplicationContextBuilder context) {
            context.environmentPropertySource(false);
        }
    }

    public static void main(String... args) {
        Micronaut.run(Application.class, args);
    }
}

Because @ContextConfigurer makes sure that any application context created will see the customizer applied, the application context created by the AOT compiler for its internal use will see the customizations.

Implementing an AOT optimizer

Current capabilities

Now that we understand how the AOT optimization environment is bootstrapped, we can start implementing an AOT optimizer.

An optimizer can do one or more of the following:

  • generate static initializers which will automatically be loaded thanks to the ApplicationContextConfigurer mechanism

  • generate new source files

  • generate new resource files

  • perform substitutions of one class with another

  • filter out resources

New capabilities will be included as part of AOT development.

Code generators

At the core of AOT optimizations is a code generator. A code generator needs to implement the AOTCodeGenerator interface and be annotated with @AOTModule.

The implementation class should be compiled from the regular Java source root of an AOT optimizer module, for example src/main/java. Register the generator with Java’s ServiceLoader mechanism by adding its fully qualified class name to src/main/resources/META-INF/services/io.micronaut.aot.core.AOTCodeGenerator. Build tool integrations load optimizer modules from the AOT optimizer classpath; for example, Gradle users can add the optimizer artifact or project dependency to the aotPlugins configuration.

The AOTModule annotation is responsible for giving metadata about the code generators, including:

  • an id is used to identify the code generator, and enable/disable it via configuration

  • a number of options (@Option) which are used to describe the parameters that the code generator takes (those are provided via configuration)

  • possibly dependencies to other code generators (for example, some code generators may only work properly if they execute after another one)

  • the target runtimes it applies to

Code generators contribute code via the AOTContext interface, which allows:

  • getting the name of the package of generated classes

  • registering generated code (source files, …​)

  • getting access to the ApplicationContext

  • sharing state

  • getting access to target runtime

For example, a simple code generator which generates a resource file may be declared as:

@AOTModule(
    id = MyResourceGenerator.ID,
    options = {
        @Option(key = "greeter.message", sampleValue = "Hello, world!", description = "The message to write")
    }
)
public class MyResourceGenerator implements AOTCodeGenerator {
    public static final String ID = "my.resource.generator";

    @Override
    public void generate(AOTContext context) {
        context.registerGeneratedResource("hello.txt", file -> {
            String message = context.getConfiguration()
                .mandatoryValue("greeter.message");
            try {
                java.nio.file.Files.writeString(file.toPath(), message);
            } catch (java.io.IOException e) {
                throw new RuntimeException(e);
            }
        });
    }
}

Then in a configuration file, the code generator would be configured this way:

my.resource.generator.enabled=true
greeter.message=Hello, world!
Different code generators may share the same option values: it is legal, but often simply required (for example if there’s a different implementation of a specific optimization based on the target runtime).

5 Precompiling logback.xml

The micronaut-aot-logback module compiles an application’s logback.xml into a Logback Configurator at build time. Without a Configurator service, Logback parses logback.xml with its Joran framework on the main thread at every start. An application that carries the generated configurator does neither.

This module is internal to the Micronaut build plugins: its API, the names it generates and its rules may change in any release.

Unlike the logback.xml.to.java optimizer, this module is not an AOT optimizer. It does not start the application, uses no AOTContext, and needs no AOT run: the Micronaut Gradle and Maven plugins and Micronaut Runner call it in-process with plain paths and get class files back. Its artifact, io.micronaut.aot:micronaut-aot-logback, has no dependencies. An application does not depend on it: its build plugin calls it.

The engine fails closed. Whenever it cannot prove that the generated code builds exactly the LoggerContext Joran builds, it generates nothing and says why, and Logback reads logback.xml at startup as it always did. It also stands down when a Configurator is already registered on the class path it is given, which is the case for an application that logback.xml.to.java has already optimized. It cannot see an optimizer that runs later, on an application that already carries its output: a build that applies both has to decide which one configures Logback.

How the build plugins call it

This section describes what the Micronaut build plugins do, for those who maintain them. LogbackPrecompiler is @Internal: it is not an API for applications or for other build tools.

LogbackPrecompiler.Result result = LogbackPrecompiler.precompile(
    LogbackPrecompiler.Request.builder()
        .applicationOutput(List.of(processedResources, classesDirectory))
        .runtimeClasspath(runtimeClasspath)
        .targetRelease(25)
        .build());
log.accept(result.message());
result.warnings().forEach(warn);
for (Map.Entry<String, byte[]> entry : result.entries().entrySet()) {
    Path file = outputDirectory.resolve(entry.getKey());
    Files.createDirectories(file.getParent());
    Files.write(file, entry.getValue());
}

The inputs are:

Input Meaning

applicationOutput

The application’s own output in class path order: its resource roots and its class directories, or a jar. Pass the class directories as well as the resources: the engine stands down when the application carries a Logback or SLF4J class, or a Configurator service file, which an annotation processor writes to the class output. When two roots hold the same name, the first wins, except for logback.xml: when two roots have one, the engine stands down.

runtimeClasspath

The runtime class path after the application, in order: jars or directories. The engine takes logback-classic, logback-core and slf4j-api from here, never from the caller’s own class path.

targetRelease

The lowest Java release the application runs on. The generated classes are class files of Java 25, so the engine stands down below 25.

closedClassPath

true only when the class path given here is exactly the one the application runs on. false by default. See Guards for open class paths.

The Result has a status(), one message() for the caller to log, the generated entries(), and warnings():

  • GENERATED: the message says what was compiled. The plugin writes the entries below a directory, which has to be on the application’s class path next to its logback.xml, or a packager adds them to an archive. All of them go to the same place: the configurator calls the classes copied next to it, which are package-private, so they have to be on the same class loader.

  • STOOD_DOWN: nothing was generated, and the message names the reason. This is expected for many applications.

  • FAILED: nothing was generated because a generated name is already taken, the output of an earlier call is still in the application output, the class path could not be read, or the engine failed. The message is worth a warning.

warnings() holds lines that the plugin logs at warning level, each on its own, after the message. Only a GENERATED result can have any, and most have none: the one case today is a packaged file that may enable distributed configuration (see Locations only Micronaut sees). The list is never null.

precompile never throws for anything about its inputs, so a build that calls it does not fail because of Logback. Removing the output of an earlier build is the caller’s job. A caller that writes into one of the application roots it passes, such as the class directory, has to remove that output before it calls precompile again, not after. While it is there the result is FAILED and the earlier output stays in use, whatever has changed in the application since. The output is the service file and the classes of the package io.micronaut.aot.logback.generated. logback.xml has to stay in the application, because the fallbacks below read it.

LogbackPrecompiler.applicationInputs() returns, as Ant-style patterns, the entries of the application output that can change the result. A build plugin may declare its inputs with them, so that the step stays up to date when ordinary classes and resources change. Of everything else in the application output the engine reads the name and nothing more. On the runtime class path it reads the names of every entry, the manifests of logback-classic and logback-core, and the packaged application* and bootstrap* configuration files of every entry.

The engine never loads application classes. It reads logback.xml with Logback’s own parser and model builder, taken from the application’s Logback jars, in an isolated class loader. It instantiates only the ch.qos.logback classes the file names, and never starts an appender.

What it generates

Three classes in the package io.micronaut.aot.logback.generated and one service file:

  • LogbackConfigurator, the configurator, as a class file of Java 25;

  • JoranFallback, which every path that hands over to Joran goes through, so that the literal path never loads Joran;

  • ClassPathGuard, unless the class path is closed;

  • META-INF/services/ch.qos.logback.classic.spi.Configurator.

The subset

The engine compiles a logback.xml made of:

  • appenders of public ch.qos.logback classes with String, boolean or int properties and at most one PatternLayoutEncoder with a pattern;

  • loggers, the root logger and appender references.

Everything else stands the engine down, and the message names the element: variables, <property>, <include>, <if>, <conversionRule>, filters, rolling policies, custom appenders and a <configuration> with debug, scan or packagingData on. So does what Joran itself corrects: two appenders with the same <file>, a property element without text, a <name> element inside an appender. The logback.xml that Micronaut Launch generates is inside the subset.

When it stands down

Besides a file outside the subset, the engine generates nothing when:

  • targetRelease is below 25;

  • the application output carries a Logback or SLF4J class of its own;

  • logback-classic, logback-core or slf4j-api is missing, a Logback jar declares no Implementation-Version, the two versions differ, or the version is outside the tested range, which is [1.5.37, 1.6);

  • there is no logback.xml, or more than one class path entry or more than one application root has one, which Logback reports at startup;

  • any class path entry has a logback-test.xml, a logback.groovy or a versioned Logback file under META-INF/versions/;

  • any entry of the class path it is given already registers a Configurator;

  • a packaged application* or bootstrap* configuration file, at the root or under config/ of an application root or of any entry of the runtime class path, may set logger.config or logback.configurationFile, or may import configuration with micronaut.config.import. Micronaut applies such a location only without a Configurator service, and the generated code cannot see it (see Locations only Micronaut sees). An import can load a class path resource of any name, a file, an environment variable or what a custom provider supplies, and what it loads can set the location or import more. The engine does not follow imports, so it stands down on any import, whatever it names. Every such file is read, also one that an earlier entry has under the same name: Micronaut reads the file of a dependency when the application has none of that name, and it can merge the files of every entry, depending on its configuration loading strategy. The names are wider than what Micronaut reads by default, which is application and bootstrap, with an optional environment suffix, at the root of the class path: config/ is read only when overrideConfigLocations adds a location such as classpath:config/. A false positive only costs the optimisation.

One case of these same files does not stand the engine down but adds a warning to a GENERATED result: a file that may enable Micronaut’s distributed configuration client (see Locations only Micronaut sees).

What the configurator does at run time

On every call, in this order:

  1. If the logback.configurationFile system property is set, it runs Logback’s own default lookup.

  2. On a second or later call, which is Micronaut’s logging refresh, it configures from the first of these that is set: an environment variable named logback.configurationFile, the logger.config system property, the LOGGER_CONFIG environment variable, an environment variable named logger.config.

  3. If logback.debug or logback.statusListenerClass is set, or -Dmicronaut.logback.precompiled=false, it runs Logback’s default lookup.

  4. On an open class path, if a guard fails, it runs Logback’s default lookup.

  5. Otherwise it applies the content of logback.xml literally, in Joran’s order.

-Dmicronaut.logback.precompiled=false is the opt-out: with it every call hands over to Joran. It does not bring back a location that only Micronaut sees, described below.

Locations only Micronaut sees

Micronaut applies logger.config, or a logback.configurationFile of its own configuration, on its logging refresh. When any logger.* property is set, that refresh runs at startup and again on every refresh event. Without a Configurator service it configures Logback from that location. With one, it calls the service’s configure(LoggerContext) and passes it nothing else: the location stays in Micronaut’s LogbackLoggingSystem, and Micronaut copies it neither into a system property nor into the LoggerContext.

So the generated configurator applies a location only where it can read it itself, as the first two rules above list: the logback.configurationFile and logger.config system properties, and the logback.configurationFile, LOGGER_CONFIG and logger.config environment variables. A location that comes from any other property source is not applied, and the compiled configuration stays in use:

  • a program argument, such as java -jar app.jar --logger.config=custom.xml. A -Dlogger.config=custom.xml written after the jar or the main class is a program argument too, not a system property: Micronaut keeps it in the property source of its command line. The configurator does not read the command line of the process instead, from the sun.java.command property or from ProcessHandle.current().info().arguments(): the command line does not say which arguments the application passed to Micronaut, and it is only one of the sources listed here;

  • a configuration file that no packaged file names: config/application.yml in the working directory; a file named by the micronaut.config.files system property or the MICRONAUT_CONFIG_FILES environment variable, on the file system or, with a classpath: prefix, on the class path; a bootstrap configuration file named by the micronaut.bootstrap.name system property;

  • configuration that micronaut.config.import imports when one of the sources of this list declares the import, whatever it imports, a class path resource included;

  • any other property source, such as distributed configuration or properties passed to ApplicationContext.builder().

Pass the location as a JVM system property, java -Dlogger.config=custom.xml -jar app.jar, or as the LOGGER_CONFIG environment variable instead. The opt-out does not help: the configurator then runs Logback’s default lookup, which reads logback.xml, because Micronaut still calls the configurator instead of reading the location. From Micronaut 5.3, the refresh applies such a location itself, whatever Configurator is registered: see micronaut-core#13400. The build can read the packaged application* and bootstrap* files, and none of the sources above. So it stands down when one of those files might set the location, or might import configuration with micronaut.config.import, which the build does not follow, wherever the import points.

Distributed configuration is one of the sources the build cannot read: it cannot know what a configuration server will supply. It can see, though, a packaged application* or bootstrap* file, of an application root or of a dependency, that may enable Micronaut’s distributed configuration client: one that sets micronaut.config-client.enabled to true or to any placeholder. The engine then still generates the configurator, and the GENERATED result carries one warning for each such file. The warning names the file and its root or jar, says that the file may enable the client, that a logger.config or logback.configurationFile that distributed configuration supplies is not applied while the generated configurator is registered, and gives the workarounds: pass the location as -Dlogger.config or LOGGER_CONFIG, as above, or turn precompilation off in the build plugin, so that no configurator is generated. It also says that -Dmicronaut.logback.precompiled=false does not help, for the reason above. A .properties file is parsed. In any other format the engine checks the text, ignoring case: the word config-client (or configClient) and an enabled key set to true, yes or on anywhere in the file give the warning. In every format, a placeholder counts as well, quoted or not (in a .properties file quotes are part of the value, so only an unquoted one counts), whatever its default and also without one: ${CONFIG_CLIENT_ENABLED}, ${CONFIG_CLIENT_ENABLED:false} and ${CONFIG_CLIENT_ENABLED:true} all give the warning, and so does the escaped "\${CONFIG_CLIENT_ENABLED}" of a double-quoted Groovy string. Micronaut resolves a placeholder at run time, from sources the build cannot see, so it may resolve to true. A false positive only costs a warning line. enabled: false, or a mention of config-client without an enabled key, gives none, unless another enabled key of the same file is set to true or to a placeholder: the text rule does not know which section a key belongs to. A client that is enabled in any other way is not seen, and gives no warning: by an environment variable such as MICRONAUT_CONFIG_CLIENT_ENABLED, a system property or properties passed to ApplicationContext.builder(); by a file outside the application and its dependencies, such as one that micronaut.config.files names; by a bootstrap configuration file whose name starts with neither application nor bootstrap, which the micronaut.bootstrap.name system property selects; or by a value that a packaged Groovy file computes, such as enabled = System.getenv('CONFIG_CLIENT_ENABLED') ?: false.

Guards for open class paths

Outside a packaging that fixes the class path, the class path can change after the build: a later test run sees the same output directory, an IDE leaves stale output, a file is mounted into a container image. So unless the caller sets closedClassPath(true), the configurator hands over to Joran when:

  • a logback-test.xml is visible, or

  • the first visible logback.xml is missing, or differs from the compiled file in size or CRC-32.

It looks where Joran would, through the class loader that defines logback-classic, and it looks again on every call. So a logback.xml that is edited while the application runs is read by Joran on the next logging refresh, as it would be without the generated configurator. Each call costs two class loader lookups, one read of logback.xml and its CRC-32. Logback calls the configurator once when it initialises, and Micronaut once per logging refresh, which it runs only when a logger.* property is set; a log call never runs the guards. The first call costs a few milliseconds, most of it the class loader’s first lookups, which the application makes later anyway; every later call takes well under a millisecond.

The guards have limits. After any of these changes the generated configurator is still applied, although Joran would give another result:

  • A second logback.xml is added to the class path after the build. Logback would report it at startup.

  • The class path changes in another way that the build checked. Nothing but the two guards is checked again at run time: not the Logback version, not a Configurator that another entry registers, not a packaged logger.config or micronaut.config.import. With a Logback outside the tested range, the generated classes are untested and may not even link.

Build again after such a change: the build then stands down, or compiles the class path as it now is. Until then, -Dmicronaut.logback.precompiled=false gives Joran’s result back in two of these cases only: a second logback.xml, and another Logback version as long as the generated classes still load. Every call then runs Logback’s default lookup, which reads logback.xml. So the opt-out does not help in the other cases. Where the generated configurator is called instead of a Configurator that another entry registers, it runs that lookup, not the other Configurator. A packaged logger.config, or one that a packaged import loads, stays unapplied, as a location only Micronaut sees (see Locations only Micronaut sees): pass it as a JVM system property or as LOGGER_CONFIG until the next build.

closedClassPath(true) is for a packager whose archive is the whole class path. The build-time checks then guarantee what the guards check, and ClassPathGuard is not generated.

6 Diagnostics Report

Micronaut AOT can write a structured diagnostics report for build tools and CI systems. The report is disabled by default and does not change generated sources, generated resources, or log files unless it is enabled.

Enable the report with the following configuration property:

micronaut.aot.report.enabled=true

When the CLI is used for an AOT run, the same behavior can be enabled with:

micronaut-aot --classpath app.jar --runtime jit --package example.aot --config aot.properties --output build/aot --report

The default output file is:

<output.directory>/reports/micronaut-aot-report.json

Use micronaut.aot.report.output or --report-output to select a different report directory. Micronaut AOT writes fixed file names inside that directory.

The default report format is JSON. The default value is:

micronaut.aot.report.format=json

Set micronaut.aot.report.format=html or micronaut.aot.report.format=json,html to write an HTML report. The CLI accepts the same values with --report-format. The fixed output file names are:

  • micronaut-aot-report.json

  • micronaut-aot-report.html

Unsupported formats fail the AOT run with a configuration error.

The JSON report uses a versioned schema. Version 1 includes:

  • schemaVersion

  • generatedAt

  • micronautVersion

  • runtime

  • packageName

  • activeEnvironments

  • optimizers, including optimizer id, implementation class, description, enabled state, disabled reason, option keys, dependency ids, and supported runtimes

  • generatedSources

  • generatedResources

  • filteredResources

  • excludedServiceImplementations

  • buildTimeInitClasses

  • diagnostics

Example:

{
  "schemaVersion": 1,
  "runtime": "JIT",
  "packageName": "example.aot",
  "optimizers": [
    {
      "id": "netty.properties",
      "enabled": true,
      "options": [
        {
          "key": "netty.machine.id",
          "configured": true,
          "redacted": true
        }
      ]
    }
  ],
  "generatedSources": [
    {
      "className": "example.aot.AOTApplicationContextConfigurer",
      "path": "example/aot/AOTApplicationContextConfigurer.java"
    }
  ],
  "generatedResources": [
    "META-INF/services/io.micronaut.context.ApplicationContextConfigurer"
  ]
}

Configuration values are not written to the report. Optimizer options only show the option key, whether the key was configured, and whether the value was redacted. This prevents common secrets such as passwords, tokens, credentials, and datasource values from being copied into diagnostics artifacts by default.

Build-tool integrations can enable the report property for an AOT invocation and publish the printed report path or the JSON file as a build artifact. When HTML is enabled, integrations can also publish micronaut-aot-report.html as a human-readable build artifact. Existing log files remain available for detailed diagnostics.

7 Rewriting the Runtime Class Path

The micronaut-aot-bytecode module rewrites the class files of an application’s runtime class path at build time. A build plugin gives it the class path and gets back a class path to package: each entry as it was, or a rewritten copy of it. The one step it has today strips the local-variable tables of the third-party jars that the plugin names (Stripping local-variable tables).

This module is internal to the Micronaut build plugins, and the step is experimental: its API, its rules and its output may change in any release.

Unlike the optimizers of Micronaut AOT, this module does not start the application, uses no AOTContext, and needs no AOT run. It reads class files and writes copies, and never loads a class of the class path. Its artifact, io.micronaut.aot:micronaut-aot-bytecode, has no dependencies, and needs Java 25 to run, for the ClassFile API. An application does not depend on it: its build plugin calls it.

How the build plugins call it

This section describes what a build plugin does, for those who maintain one. ClassPathTransform is @Internal: it is not an API for applications.

ClassPathTransform.Result result = ClassPathTransform.run(
    ClassPathTransform.Request.builder()
        .classPath(runtimeClasspath)
        .outputDirectory(outputDirectory)
        .stripLocalVariables(thirdPartyJars)
        .build());
log.accept(result.summary());
result.warnings().forEach(warn);
List<String> report = new ArrayList<>();
for (ClassPathTransform.Result.Entry jar : result.entries()) {
    report.add("%s\t%d\t%d\t%d\t%d\t%s".formatted(jar.path(), jar.classesStripped(),
        jar.classesUnchanged(), jar.fallbacks(), jar.bytesSaved(), jar.kept().orElse("")));
    report.addAll(jar.notes());
}
Files.write(reportFile, report);
List<Path> packaged = result.classPath();

The request takes:

Input Meaning

classPath

The runtime class path, in the order the application’s class loader searches it, the application’s own output first: jars or directories. Required. Every class on it is part of the model that a rewritten class is verified against, so pass the whole class path, not only the jars to rewrite.

outputDirectory

Where the rewritten copies go. Required. A copy is written under a subdirectory named by the index of its entry in classPath, with the entry’s own file name, so two entries with the same file name never collide. The caller owns the directory and cleans it. It must not hold an entry of classPath, such as a copy that an earlier run wrote there, because a run replaces and deletes files in it: the request is rejected otherwise. Run again from the original class path into a clean directory.

stripLocalVariables

The jars whose classes are stripped: third-party jars only, each an entry of classPath. Never pass the application’s output, a module of the application’s own build, such as a Gradle project dependency or a module of the Maven reactor, or a directory: their classes are user code, and users debug their locals. The request is rejected when a jar is not an entry of classPath, when it is a directory, and when no jar is named, because the request then enables no step.

parallelism

The number of worker threads, by default the available processors. The output does not depend on it.

The Result has:

  • classPath(): the class path to package, in the order of the request. A jar with a rewritten class is replaced by its copy, which keeps the jar’s file name, so the Class-Path attribute of a manifest that names it stays valid. Every other entry is returned as it was given, and keeps its bytes and its hash.

  • summary(): one line to log, such as Stripped local-variable tables from 7102 of 8428 dependency classes in 49 jars (4868965 bytes saved, 0 fallbacks).

  • warnings(): lines to log as warnings, each on its own. Usually empty, never null.

  • entries(): what the step did to each jar named by stripLocalVariables, in class-path order, for the plugin to write under the build’s reports in its own format; empty when the step stood down because of a library that reads local-variable tables. The counts are numbers, so nothing needs parsing. Each Entry has:

    • path(): the jar, as classPath gave it;

    • classesStripped(), classesUnchanged() and fallbacks(): the jar’s classes that lost their tables, that were left as they were, and that were written as they were because the step failed on them or their rewrite verified worse. Each class of the jar counts once;

    • bytesSaved(): how many bytes smaller the stripped classes became, uncompressed;

    • kept(): why no class of the jar went through the step, such as the jar is signed, or empty;

    • notes(): one line per fallback, tab-separated: the jar, the class, the step and the first verification error or failure.

run throws only when it cannot read a jar it rewrites, or cannot write a copy. A class that it cannot parse, rewrite or verify is written as it was, and a note of its jar’s entry names it. The module logs nothing.

A copy holds every entry of the original jar, in the same order, with the same name, comment, time and compression method, and the manifest as it was. Only the classes that a step rewrote change; every other entry keeps its content. DEFLATED entries are compressed again, so the copy’s compressed bytes depend on the JDK that writes it. A signed jar, and a jar that holds an entry name twice, are left as they are.

The rewritten bytes depend on the JDK build that runs the transform, for example through the order of the constant pool. The output is reproducible, whatever the parallelism, only with the same JDK build. A plugin therefore runs the transform on the project’s Java toolchain and makes the toolchain’s version an input of its task.

The transform belongs to packaging, not to development. A plugin applies it to fat JARs and Docker images, and runs it before anything that records the jars' sizes or modification times, such as the training of a JDK AOT cache. It does not apply it to run tasks, tests, IDE class paths or native images, which do not package the class path or do not load class files at run time.

Stripping local-variable tables

Compilers write the names and types of local variables into class files, for debuggers. At run time, only debuggers, the variable names in helpful NullPointerException messages and a few libraries that parse class files read them. Without a JDK AOT cache, the JVM still parses them, and the constant-pool entries that only they use, for every class it loads. The step removes them from the classes of the jars named by stripLocalVariables. The jars get somewhat smaller, and a start without a JDK AOT cache slightly faster. With a JDK AOT cache, which holds classes already parsed, the step makes no difference worth having, and it is off unless a plugin turns it on.

The step drops:

  • LocalVariableTable, LocalVariableTypeTable and CharacterRangeTable;

  • the type annotations of method code, which hold bytecode offsets that a rebuilt constant pool can move;

  • RuntimeInvisibleTypeAnnotations on classes, fields and methods, which nothing reads at run time.

It then rebuilds the constant pool, which removes the names and signatures of the locals: dropping the attributes alone would save almost nothing.

It keeps LineNumberTable, SourceFile, SourceDebugExtension, MethodParameters, Signature and every other annotation. Stack traces keep their File.java:N frames, and reflection sees the same parameter names, generic signatures and annotations.

It leaves a class as it was:

  • when the class has an attribute that the JDK does not know, because such an attribute may hold constant-pool indexes that a rebuilt pool would break;

  • when the class is a module-info;

  • when the jar is signed, because its manifest holds a digest of every entry;

  • when the rewritten class is not smaller;

  • when the step fails on the class, or when the rewritten class verifies worse than the original.

Each rewritten class is verified with ClassFile.verify against a model of the whole class path, never against the class path of the build tool. A class that already failed to verify, for example because it references an optional dependency that is absent, is accepted when the rewrite fails in the same way.

Costs

All of them fall on the code of the stripped jars only:

  • A helpful NullPointerException message names a local variable by position, because "<local1>" is null. The line number is still there.

  • A debugger shows no local-variable names.

  • getDeclaredMethods() can return a class’s methods in another order. That order is unspecified, but code that relies on it can notice, such as a JSON mapper that orders the properties of a dependency’s type by method.

  • A rewritten class has new bytes, and software composition analysis tools may report the rewritten jars as modified.

  • The output is reproducible only with the same JDK build. A Docker image layer that holds the rewritten jars changes when the JDK build that runs the transform changes.

Libraries that read local-variable tables

Paranamer’s BytecodeReadingParanamer, AspectJ’s weaver and Spring’s LocalVariableTableParameterNameDiscoverer (before Spring 6.1) read local-variable tables at run time. When any entry of classPath contains one of them, by entry name, the step strips nothing, and warnings() holds one line that names the entry and the class. A plugin documents how to silence the warning: turn its option off.
